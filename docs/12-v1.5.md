# 12 — v1.5 Modules (Reports · Audit & Permissions · Proposals/Invoicing)

Three smaller specs, one file. All depend on core shipping first.

---

## A. Report Generator

Monthly client report assembled from data already in the system, rendered to branded PDF and a portal page.

**Sections (per-account toggles):** headline metrics vs. last period (from metric rollups) → content shipped (published posts w/ thumbnails + top performers) → creative wins (winning creatives + learnings, client-safe wording) → work completed (done tasks, grouped) → next month (upcoming slots, open items) → optional AI narrative summary (temp 0, numbers-sourced-only rule; a member edits before send).

**Flow:** cron drafts on the 1st → member reviews/edits in a report editor → publish = PDF to portal + digest email. Never auto-sends.

```
reports — account_id, period, sections jsonb, status (draft|published), pdf_file_id
```

- [ ] Section assemblers over existing rollups
- [ ] Editor + AI narrative
- [ ] PDF render (server-side, branded template) + portal page

## B. Audit Log & Granular Permissions

**Audit log:** one append-only `audit_log` (actor, action, entity, entity_id, diff jsonb, ip, at) written from the service layer via a `withAudit()` wrapper — not sprinkled per-route. Admin UI: filter by actor/entity/account/date. Retention 2 years.

**Permissions v2:** members get per-account scoping (contractor sees only Accounts X, Y). Implementation: memberships already exist — add `role='member'` rows there and flip the middleware default from "members see all" to "members see membership accounts" behind an `org_settings.scoped_members` flag, so nothing changes until you turn it on. Add two capability flags on users: `can_manage_billing`, `can_delete` (soft-deletes only for everyone else).

- [ ] withAudit wrapper + audit_log + admin viewer
- [ ] Scoped-members flag + middleware change + contractor invite flow

## C. Proposals & Invoicing (integrate, don't build)

**Proposals:** generate a proposal draft doc from a lead (Brain-style prompt using lead record + meeting summaries + service catalog), export to PandaDoc/Docusign via their API for e-sign. Signed webhook → flips lead stage in GHL + spawns onboarding (doc 10). We store `proposal_id`, status, value — the document lives in the e-sign tool.

**Invoicing:** Stripe. `stripe_customer_id` on accounts; retainer = Stripe subscription; overages (from time tracking rollup, when built) = draft invoice items a human approves. Webhooks update a small `billing_status` per account (current | past_due) shown on the account header — past_due is a visible red flag for the whole team.

```
proposals — lead_id, external_id, provider, status, value_cents, signed_at
```

- [ ] Proposal draft prompt + PandaDoc adapter + signed webhook → onboarding
- [ ] Stripe customer/subscription linkage + status webhooks + header flag
